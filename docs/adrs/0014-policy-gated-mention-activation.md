# 0014 - Policy-gated mention activation

## Decision

A canonical mention may activate a linked participant only under a per-thread activation policy that the human enabled through the UI. Choosing a recipient by similarity, free text, or an LLM stays forbidden. This ADR supersedes only the routing part of [ADR 0004](0004-no-automatic-agent-routing.md).

- The policy is off by default and revocable. Revoking it stops new activations immediately.
- Activating is not authorizing. An activation does not approve commands, accept deliveries, skip `OK_BOOTSTRAP` or handoff, or close threads.
- Only the human and participating architects trigger an activation. A developer message never activates an agent.
- A mention activates only within its own thread.
- A `role: user` message in `CHAT.md`, or one sent through MCP, does not enable, renew, or extend anything. Only UI controls recorded by the daemon do.
- An authorization pins the revision and a hash of the policy content, without `revision` and `updatedAt`. A hand edit of `policy.json` that changes the content fails closed, even when the revision is unchanged. Saving through the UI creates a new revision and reconciles the pin.
- A thread whose `SUMMARY.md` exists accepts no daemon write. Its daemon state and its `policy.json` are removed, at startup and when the `SUMMARY.md` appears, and a late heartbeat, release, observation, acquisition, reservation, or conflict is refused.
- With the policy enabled, a mention of an architect without an open session creates a card in the activation panel, and nothing starts until the human approves that card. F4 approves once per agent and thread: the first Approve of an architect records its approval under the policy revision in force, and that architect's later awaiting cards in the thread start on their own, judged in the same queue as an Approve, within the cycles and the other gates. The approval holds until the policy is saved again or switched off, and a save clears every approval. Retry and continue of a failed turn stay manual.

F4, decided on 13/11/2026: asking whether to listen to a thread is the product default. Its default lives in the workspace settings as `listening.defaultOn`, off unless the human turns it on. Off has the principal agent ask whether to listen when it starts on a thread; on has it listen and offer to stop. Only the principal, which works with the human directly in an interactive session, follows this; a delegated developer or a turn that runs once never arms a listener. The default listening time limit is 8 hours (480 minutes). The setting is a preference and authorizes nothing, so every bullet above still applies.

### Principle: mechanism in mARC, process in RULES

mARC offers the mechanism: who wakes whom, how many cycles a stage may use before the loop stops, and the brake the human controls. The way a workspace works comes from its `RULES.md`. The three fixed stages (Planning, Execution, Review) are the macro fit for those phases: an agent maps each RULES phase to one of them. A thread with no agent-to-agent collaboration stays with the switch off and works as before.

### Phases

- F3a stores the policy, the pause and the counters. Nothing activates.
- F3b activates under the policy: the reservation of each mention, the cycle budget, retained reservations, the stage moves, and the lead.
- Each mention that the policy allows reserves its message with the daemon before the waiter releases it. `marc wait` exits with code 0 (granted), 7 (held until the deadline; nothing advanced), 8 (`activation_refused`, with a reason) or 9 (`daemon_unavailable`, fail closed).
- The supervisor and the client adapters belong to F3c.
- F3c adds the supervisor in confirm mode, the Claude Code client adapter, the turn time limit, the recovery after a daemon restart, and the permission prompts of a supervised turn, as described under Consequences.

## Context

[ADR 0004](0004-no-automatic-agent-routing.md) keeps mARC from deciding which agent should act, because automatic routing would add hidden behavior too early. A mention that wakes an agent needs an explicit human decision, recorded where the human acts. Thread a54ceabc set the rules for that decision: a per-thread policy, a budget per stage, a substitute ADR for the routing part of 0004, and a local state that fails closed.

Policy state is split by ownership. `policy.json` in the thread folder is versioned configuration, allowed as JSON by [ADR 0001](0001-markdown-source-of-truth.md). Session slots, activation counters, reservations, and stage history live in one state file per thread under the daemon data directory, and the pause lives in one file per workspace. That state is local and outside the repository, so a commit cannot pause another machine. Each file has its own write queue, and each is written with a marker first, so a lost file reads as lost and not as a fresh start.

## Consequences

- `policy.json` (version 2) is structured configuration: the switch, the mode, the revision and two limits. The UI routes are the only writers of the policy, the pause, the cycles setting, the human stage moves and the lead. No MCP tool sets any of them.
- Stages are fixed: Planning, Execution and Review (the ids are planning, execution and review). Users never edit their ids or exit conditions. A thread can start directly in execution or review. Participants are every architect-role profile, computed live and never stored. A new architect profile does not pause an enabled thread.
- **Cycle.** One architect round trip. A mention that opens a cycle debits one cycle of the stage stamped on the mentioning message, or of the current stage when the message has no stamp. A mention that answers an open cycle in the other direction closes it without a debit. A stage's cycles are counted per stage and never carry over.
- **Budget.** The default is five cycles per stage, set by `activation.cyclesPerStage` in `marc.config.json` (integer 1 to 20). The file is trusted only through the authorization the daemon records on each UI save of the setting. A hand edit pauses every enabled thread with `settings_tampered`. The ceiling per thread is 3 × N, where N is the authorized cycles per stage, plus the cycles the human grants with `More N cycles`. Advancing never lowers a counter.
- **Lead.** The lead is the focal point of the thread: the agent the human asks about what is happening. The default is the first `CHAT.md` author whose profile has the architect role. The human changes it from the panel with `Make lead`, which sends `{ agentId, expectedLead }`; a stale `expectedLead` is refused as `lead_changed`, and only an architect profile can lead. A change moves the lead and nothing else: the budget and the stage stay as they are. Only the lead advances the stage as an agent.
- **Advance by the human.** The panel offers every stage ahead, through `POST …/activation/advance` with `{ expectedStage, to }`. The destination must be strictly ahead, so a planning thread can go straight to review. Skipping a stage loses only the unspent cycles of the stage skipped, and nothing transfers. The human can leave an exhausted stage.
- **Advance by the agent.** The lead posts with `advanceTo` in `message_post`. The daemon checks, on the thread queue: the agent is the lead, its identity is verified, the expected stage is current, the stage is not exhausted, the destination is ahead, and the stage is not the last one. A refused advance does not block the post: the message is written without moving the stage, and the result carries `stage_advance_refused` with its reason. The message that advances carries the destination stage and no cycle. If the append fails after a granted advance, the advance stays with a `null` reference and the append error propagates. A timeout does not prove a refusal: the post is written and the result carries `stage_advance_unknown`. The tool `thread_advance_stage` is removed; the advancing message is the reference. The reference is evidence for audit, not proof of consensus.
- **Reservation.** Before a waiter releases a mention, the daemon grants a reservation keyed by message and recipient. The request carries only `messageId`, `recipient`, `holder` and `runId`. The daemon reads the author, the mentions and the stamp from the canonical message in `CHAT.md` and never trusts a sender the client names. A reservation is refused as `ineligible_origin` when the recipient is not among the message's mentions, or when the message is a `role: user` message that did not go through the UI route.
- **Holds.** When the thread cannot proceed (budget exhausted, a paused workspace, a state that the panel resolves), the reservation is retained with its reason, and the waiter keeps waiting. A retained reservation spends no attempt. The human resolves it in the panel with `More N cycles`, `Resume`, or by advancing. An advance drops the retained reservations of earlier stages with `stage_advanced`, counts them in `droppedHolds`, and shows the count before the human confirms.
- **Attempts.** A delivery of the same holder and run is idempotent. A new delivery of a granted reservation counts an attempt up to `attemptCap` (default 2), then `attempts_exhausted`. A granted reservation is never reversed, not even on a waiter timeout. Pruning keeps a `prunedThrough` floor, so a pruned grant does not produce a second debit.
- **Stamp.** A message block carries optional `stage` and `cycle` fields. The former `pass` field is `cycle`; no record used it before. Agents never set them. The MCP asks the daemon in two phases: prepare, which reads the stage and the cycle of the author's open granted reservation, and confirm, which links the `messageId` after the message is persisted. Each call has a timeout of 1.5 seconds. Without the daemon, the message is posted without the stamp and the result carries a warning. Older records render unchanged.
- **Restoration floor.** When the highest cycle stamped in a stage is greater than the cycles counted for it, the thread pauses with `ledger_restored`. Recover raises each stage's count to that highest stamped cycle, and no count goes down. Recovery is a human action; when everything is healthy it is refused as `nothing_to_recover`.
- **Waiter exit codes.** In a thread with an enabled policy, `marc wait` uses 7 for a hold that outlived the deadline, 8 (`activation_refused`, with a reason) for a definitive refusal, and 9 (`daemon_unavailable`) when the daemon cannot be reached. The F3a code 8 `policy_active` is removed.
- A lost or invalid state file refuses writes and is never silently recreated. Recovery is a human action: invalid content moves aside under a timestamped name and is never deleted, and every enabled policy stays unauthorized until it is saved again.
- The closing activity section records profiles, origins, stage outcomes, stage moves with their message ids, lead changes, and the policy revision. It never records native session identifiers, process identifiers, or hosts. When a configured daemon cannot be asked in time, the section records that the activity was not recorded, and the closure still goes through. With no daemon configured the section is omitted.
- The legacy `sessions.json` is split once into per-thread files. The original is renamed with a migration suffix and is never read again as a fallback. A completion marker, `sessions.migration.json`, is written after the split; once it is valid, a legacy file that reappears is ignored. A missing marker with partial state reruns the migration, and an invalid or lost legacy registry keeps failing closed.
- A version 1 policy from F3a is read without failing and never authorizes anything. An enabled one reads as `policy_outdated` and pauses until the human saves it again. The save maps an unknown stage to planning only with the human's explicit confirmation, shown before saving. Legacy counters are kept as history and never converted into cycles.
- Limits such as time and cost stay separate from the cycle budget. No monetary limit blocks an activation in this phase.
- **Supervisor, confirm mode.** A mention of an architect profile with no open session creates a card. The card has a reason and no action while the daemon cannot start the turn (busy, not listening, another host, an unverified session, or a paused workspace), and it has `Approve` and `Decline` when the start is possible. Approve judges the card again on the thread queue: the policy revision and its content pin, the pause, the cycles setting, the turn time limit, the reservation verdict, the slot and the posse. It then takes the posse with origin `supervisor`, reserves the cycle under the stable holder `supervisor:<messageId>:<recipient>`, and writes the card as `starting` with a new run identifier, in one write. A refusal writes nothing, so no posse is left without its card. A second pass runs just before the process starts; if the revision, the generation or the card changed, the turn does not start and the card fails as `revoked`, and the reservation keeps its debit.
- **Card lifecycle.** A card is `waiting`, `awaiting_confirmation`, `starting`, `running`, `failed`, or one of the final states `done`, `declined`, `expired`, or `superseded`. A reply in the thread supersedes a card that was not yet approved. A card that is not acted on expires after the policy's pending TTL (`pendingTtlMinutes`, 1,440 by default) and then counts only in Activity. Starting and running cards never expire, and the daemon prunes only the terminal cards beyond 50, keeping each recipient's floor so that a pruned card is never recreated by a later pass.
- **Client adapter.** The launch goes through a table of client adapters. The Claude Code adapter runs `claude -p` headless, without a shell, without `--bg` (which would copy the session), and without stdin. A new session takes an identifier that mARC generates and records before the start, passed with `--session-id`; a known one resumes with `--resume`. The adapter fixes `--model` to the profile's model, checks that the result reports the expected session, and maps the failure reasons (`session_not_found`, `auth`, `client_missing`, `timeout`, `crashed`, `invalid_output`, `error`). A timeout or a crash takes precedence over an incomplete JSON result, and an ambiguous diagnosis stays `error`. The profile's `Client:` line (`claude-code` or `codex`) is read first; without it, the model prefix decides, as before. A `codex` profile has no adapter until F5 and is refused as `unsupported_client`. `agent_register` accepts `client` as an optional field.
- **Origin `supervisor`.** A posse taken by a supervised turn carries the origin `supervisor`. The slot shows busy while the turn runs, a `marc open` on that slot is refused as `reserved`, and the slot becomes `ended` when the turn releases it, which lets the next mention resume the session after a new approval, or on its own when the architect is approved in this thread (F4).
- **Turn time limit.** `activation.turnTimeoutMinutes` in `marc.config.json` is an integer from 15 to 480, default 60, saved from the workspace settings with the same UI authorization as the cycles setting. It applies only to turns the supervisor starts; a session the human opens is never stopped by mARC. In the last 10 minutes, every mARC tool response to the turn, identified by `MARC_SUPERVISOR_RUN_ID`, carries the minutes left and asks it to finish the current change and post its progress. At the limit, those responses ask it to stop now, and the daemon gives the turn 2 minutes of grace. After the grace, the daemon ends the turn's process tree: `taskkill /T /F` on Windows, and the process group on POSIX. The card then reads `failed: timeout` and offers `Continue`, which resumes the same session with a prompt to check what was left half done. Continue revalidates the authorization and the attempt cap, keeps the same holder, and debits no new cycle. Files already written stay on disk.
- **Recovery after a restart.** After a daemon restart, the supervisor does not decide any card that depends on presence before a full lease TTL (45 seconds) has passed, and until then the card shows `Checking sessions`. Each `starting` or `running` card is then reconciled by its process identifier and start instant. A live process keeps its posse, its deadline is rearmed, and its end is recorded as `done`. A process that is gone becomes `failed: crashed`. The reconciliation writes once, with no second writer and no refund.
- **Permission prompts.** A supervised turn starts in the client's automatic permission mode, `--permission-mode auto`, and names `mcp__mcp-marc__permission_prompt` in `--permission-prompt-tool`, so the client asks the workspace's mARC MCP server about what the automatic mode still asks. The panel shows each open request with its tool, a summary of its input of at most 200 characters, and `Allow` or `Deny`. A request is bound to its turn through the MCP process: its parent must be the turn's process, checked by identifier and start instant, and the request must match the active slot and generation. The decision comes only from the panel. A request without an answer in 10 minutes is denied with `timeout`, and a request still open when the turn ends is denied with the reason of that end. The turn is never resent. The answer uses the client's own contract, one text block with the `behavior` JSON, without the mARC envelope.
- **The fixed server name.** The permission tool's name is built from the server name `mcp-marc`, which is one constant in the code. A workspace that names its MCP server differently cannot receive these prompts until that constant changes.
- **Cost.** The turn's cost is the delta of `total_cost_usd` against the last value seen for that session, kept on its binding, so a resumed session does not count its history twice. The card shows it, and Activity sums it. A turn whose output was not read has no cost of its own; the next turn of the same session includes its spend in its delta. The card omits the cost in that case. It is an estimate at API prices. A turn started with `claude -p` on a subscription consumes the same quota, so the figure is not a bill.
- **Activity.** The closing section adds the supervised activations, the failed cards, the expired cards, and the estimated cost, as counts and one sum. No identifier, process identifier, or host is written.

## Limits

- **Codex identity.** The Codex profile has no verified identity until F5, so the daemon refuses its agent advance as `identity_unverified`. Its posts are still written. The human advances it from the panel.
- **Shared token and cooperating interfaces.** The protection covers cooperating interfaces that use the daemon token and the documented routes. A holder of the shared token could forge the process identifiers that an identity check reads. This does not defend against a hostile local process.
- **Evidence, not consensus.** A reference to the advancing message shows where the architects agreed; the agreement itself stays the architects' responsibility, and the human checks the cited message.
- **Skipped stages.** Skipping a stage does not prove that the RULES phases mapped to it were completed.
- **Shared bearer on the decision routes.** The panel's routes (approve, decline, retry, continue, and the permission decision) use the daemon's bearer token, like every API route. An agent that reads that token could decide its own permission request or approve its own start. This is the limit of cooperating interfaces, not a defense against a local process that reads the token.
- **Cooperative deadline notice.** The warning and the stop request reach a turn only through the responses of mARC tools. A turn that makes no mARC call sees neither, on any operating system. The forced stop does not depend on the turn.
- **Forced stop proven on Windows.** The tree kill was exercised on Windows, on the machine that ran the tests. The POSIX branch is covered by a unit test of its table only. It stays a declared limit until a POSIX machine runs the stop end to end.
