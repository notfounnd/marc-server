# Resultado F0 — frente Codex

**Responsável:** codex-dev, execução delegada Codex. **Classificação:** investigação empírica descartável do cliente, sem mudança de produto. **Revisão integrada anterior:** aprovada pelo principal; este complemento registra as provas pendentes e aguarda a revisão final do principal.

## Escopo e método

Foram cobertas as 14 células pedidas, sem consolidar uma matriz entre clientes. As células sem TUI eram A3, B2, C2, D7, E1, E2, E4 e G1; as células com TUI eram A1, A2, B3, C1, D3 e D6. O trabalho ficou em Temp/marc-f0/X, sem Git, instalação ou alteração de configuração do usuário. ConPTY usou apenas o node-pty 1.1.0 já instalado. As TUIs remotas usaram App Server privado em loopback 127.0.0.1; o modo de sandbox reportado por MCP não foi tratado como prova de isolamento do Windows.

Para concluir as células pendentes, a autorização humana permitiu executar os drivers Node do controlador fora da sandbox, apenas sob X. Ela não alterou a política dos clientes: TUI e App Server continuaram read-only/on-request. Nenhum estado global foi alterado. As retomadas conformes de D3 e D6 usaram somente o atalho nativo `y` para a aprovação pontual, sem Enter nem grant persistente. Uma tentativa D3 anterior selecionou `1` e depois enviou Enter; está preservada como desvio, separada da prova conforme. B3 usou o `1` pontual autorizado e concluiu o turno.

O perfil compartilhado codex-dev foi usado com gpt-6-luna e xhigh, conforme confirmação humana do modo registrada no despacho; os rollouts válidos registram CLI 0.166.0, modelo e esforço. Não houve introspecção do perfil. A primeira falha de autenticação G1 não gerou uso observável e não comprova custo zero.

## Comando/API e modo de execução por célula

Os rollouts válidos registram CLI 0.166.0, gpt-6-luna e xhigh. Nas formas headless abaixo, codex.exe é o launcher nativo; <cwd>, <UUID> e <prompt> são placeholders cujos valores estão nos JSONs ou drivers citados por célula. O prefixo global efetivamente usado foi --model gpt-6-luna --config model_reasoning_effort=xhigh --sandbox read-only --cd <cwd>. As formas observadas para os turnos foram:

    codex.exe --model gpt-6-luna --config model_reasoning_effort=xhigh --sandbox read-only --cd <cwd> exec --json --skip-git-repo-check <prompt>
    codex.exe --model gpt-6-luna --config model_reasoning_effort=xhigh --sandbox read-only --cd <cwd> exec resume --skip-git-repo-check <UUID> --json <prompt>

A CLI exec/resume não passou --ask-for-approval e a política observada foi never; o probe B2 falhou fechado sob essa política. A3 e C2 acrescentaram --no-daemon ao prefixo global; G1 não passou essa flag.

A forma TUI remota registrada foi codex.exe --remote ws://127.0.0.1:<porta> ... --ask-for-approval on-request --no-alt-screen <prompt>, com argumentos completos e valores preservados no JSON de cada controle. TUI e App Server privado foram configurados com on-request. As chamadas de App Server citadas abaixo usaram thread/start, thread/resume e turn/start; onde indicado, o host respondeu accept ou decline à solicitação MCP. As TUIs conectaram ao App Server privado em loopback; não se usou daemon global nem a variante --no-daemon para TUI. A telemetria de MCP informou sandbox_mode=read-only e sandbox=none; ela não demonstra isolamento efetivo do sistema operacional.

Os clientes remotos B3 usaram --remote <addr> --cd <cwd> --no-alt-screen resume <UUID>, herdando a configuração read-only/on-request do App Server privado; os argumentos completos e UUIDs estão no JSON.
